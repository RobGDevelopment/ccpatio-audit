CC Patio — remediation record and audit response

Production origin — ccpatpvlive 18 September 2026 Prepared by PrimeView

Purpose

This document records the remediation work carried out on the CC Patio production environment (ccpatpvlive), in response to the request items raised on 27 August 2026 and to the architectural audit circulated on 18 September 2026.

It serves two functions. First, it documents what was changed, when, and what the resulting measurements show. Second, it supplies context on six findings where the available evidence did not show the full picture.

On that second point we want to be clear about where the gap sat. The questions raised were reasonable ones to ask, and in several cases they were the right questions asked against incomplete information — a Site Health export shows plugin and constant state, but not server-level configuration, scheduling intervals, how components relate to one another, or where a task sits in the project sequence. That the reviewer could not see those things is a reporting gap on our side, not an error on theirs. Where our records or live checks show a different position, we have set out the evidence rather than simply asserting the correction.

How this document was prepared

Rather than respond to the audit from recollection, we ran an independent audit of the production environment on our own side and compared the two sets of findings item by item. Ours was a live, authenticated read-only assessment of www.ccpatio.com carried out using our internal audit tooling (EMCP), covering: current runtime versions, WordPress configuration, plugin and theme inventory, database footprint, scheduled actions, server-side performance, malware heuristics and core integrity, hardening posture, Elementor structure, sampled SEO and accessibility, and internal-link integrity. No content, configuration, files, plugins, users or database records were changed during it.

The two assessments differ mainly in evidence base, which accounts for most of the discrepancies between them. The report we received was reasoned from a WordPress Site Health information dump — a text snapshot of a moment in time. Ours queried the live environment directly. Where a Site Health snapshot reports that a plugin is active but not how it is scheduled, or that two components are installed but not how they relate, the live check can resolve the difference.

Where our own audit confirmed a finding in the report we received, we have said so plainly. Where it produced a different result, the live evidence is cited. Items we consider genuinely open are listed at the end without qualification, and several findings in the report are correct and are being tracked accordingly.

2. PHP runtime upgrade

The audit lists PHP 8.2 end-of-life as a CRITICAL finding. This has been resolved.

The ccpatpvlive origin has been moved from PHP 8.2.33 to PHP 8.3.33, a supported release receiving security patches. This can be verified in Site Health at any time.

We also attempted PHP 8.4 in the same window, and reverted to 8.3.33 the same day.

To be precise about what happened: the WordPress admin and several product templates were incompatible with 8.4 — they did not render correctly under the newer runtime. Nothing was damaged, no data was affected, and reverting the PHP version restored normal behaviour immediately. The incompatibility was a property of the runtime version, not a change to the site.

The cause is upstream rather than anything in the site's own configuration. Several plugins in the current stack do not yet have releases that declare PHP 8.4 support. Until those vendors ship compatible versions, moving the runtime forward would reintroduce the same rendering issues no matter how the upgrade is sequenced. The dependency is on the plugin authors, not on work we can complete ourselves.

We should also note the method: the attempt was made on the production origin rather than the development site. That was the wrong place to test it, and the retry will be run on dev first. We raise this rather than leave it to be inferred from the absence of the word "staging" in this section.

The sequence from here is: monitor the relevant plugins for PHP 8.4-compatible releases; once available, install them on the development site and run a compatibility matrix across WooCommerce, Elementor and the caching stack; then schedule a production runtime change with a rollback path agreed in advance. In the meantime the site runs on PHP 8.3.33, which is supported and receiving security patches, so there is no urgency forcing the move.

The practical consequence is that the audit's proposed causal chain for the intermittent HTTP 522 responses — end-of-life PHP combined with a saturated OPcache under LiteSpeed — no longer holds, since neither of its two components is present. The OPcache side is covered in the next section.

3.1 Persistent object cache

Both audits record the absence of a persistent object cache, with the read-only audit describing it as a high-value missing layer. This has since been addressed: a Redis object cache plugin has been installed and enabled on the site.

OPcache and an object cache solve different problems, and the site now has both. OPcache stores compiled PHP opcode, removing recompilation on each request. A Redis object cache stores the results of database queries and WordPress transients between requests, so repeated work — option lookups, WooCommerce product and taxonomy queries, session data — is served from memory rather than re-queried against MariaDB each time. On a catalog site with a 513.9 MiB database this removes a meaningful share of repeated query load from the origin.

We will monitor hit ratio and watch for serialization errors over the coming period, as the audit's own acceptance criteria suggest.

4. Cache topology — single HTML cache owner

The audit describes a double-proxy stack and a double HTML cache, with purge races and competing TTL policies between NitroPack and Cloudflare. We would like to clarify how the two layers are actually scoped, as this is a configuration-level distinction that a Site Health dump cannot surface.

NitroPack is the sole HTML and page cache owner. Cloudflare sits in front of it as a reverse proxy and WAF, primarily to mask the origin IP address for security purposes. Cloudflare HTML caching and APO are not in use on this zone. There is therefore one owner of page caching and one purge path, not two competing ones.

We raise this because the audit's recommendation — choose one HTML cache owner between Cloudflare and NitroPack — has already been implemented. The remaining work is documentation rather than reconfiguration.

One point of possible confusion worth naming directly: the read-only audit observed Cloudflare returning HIT during validation. That is expected and is not evidence of a second HTML cache. Cloudflare caches static assets (CSS, JS, images, fonts) by default on any proxied zone, independently of whether HTML caching is enabled. A HIT on a static asset and a HIT on a cached HTML document are different things, and only the latter would indicate overlapping page-cache ownership.

One consequence worth stating plainly, since it affects the remediation plan: our delegated access does not extend to editing zone-level configuration. We can prepare the header set and a staged CSP policy, and test them against checkout, forms, video and third-party widgets, but applying them to the zone requires action by CC Patio's Cloudflare account holder. The same applies to providing the current Cache Rules configuration for confirmation. We flag this so the dependency is understood now rather than read later as a commitment we did not meet.

5. Plugin overlap findings

We are reviewing every plugin the audit identifies as duplicating another's function, and the sections below set out where that review currently stands. Two of the groupings turn out to contain components that perform different jobs, which we have explained rather than actioned. The remainder are genuine redundancies and are being worked through.

In general, plugin lists show what is installed but not how the components relate to one another, which is the distinction these sections are drawing. Where a redundancy is real, our approach is to inventory what depends on the plugin before deactivating it, rather than removing it and discovering the dependency afterwards on a live commercial site.

5.1 Page builder architecture

The audit groups four components under "page builders / theme" and describes a dual builder bootstrap cost.

ComponentActual role
Astra + Astra ProThe active theme — the foundation all templates and styling depend on. Not a page builder.
ElementorThe page builder core.
Elementor ProAn extension of Elementor, not a separate builder. It cannot run without Elementor core and adds widgets and template features to the same engine.
Spectra LegacyA block-editor library from Astra's developer, integrated with the Astra ecosystem. Not a page builder. A consolidation candidate, subject to a block-dependency check.

There is one page builder on this site. Elementor and Elementor Pro appear as two entries in a plugin inventory because they ship as two files, but they load as a single builder — the Pro plugin has no independent rendering stack of its own. The practical bootstrap cost is therefore lower than a count of four components would suggest.

Similarly, Astra cannot be removed or consolidated away, because it is the theme. Removing it would take the site down rather than reduce load. A theme and a page builder are complementary layers, not competing ones.

On Spectra Legacy: Spectra is a block-editor plugin from Brainstorm Force, the same developer as Astra, and is built to integrate closely with the Astra ecosystem. It is a block library for the WordPress editor rather than a page builder in the Elementor sense, so its presence does not constitute a second builder stack.

We accept that it is a consolidation candidate. Before deactivating it we are inventorying which pages still render Spectra blocks, because where those blocks are in live content, removing the plugin would break the rendered page rather than simply reduce load. That inventory determines whether it can be retired outright or whether the affected pages need rebuilding in Elementor first.

The audit's related observation about 77 Elementor templates — including export copies, backups and legacy headers — is fair, and template housekeeping can be scheduled as separate work.

5.2 Security and access control stack

The audit describes Wordfence, Limit Login Attempts Reloaded and WPS Hide Login as a pile-up with overlapping authentication gates. These three address different attack surfaces and are better understood as layered controls:

PluginFunction
WordfenceWeb application firewall, malware and core-integrity scanning, traffic-level threat blocking
Limit Login Attempts ReloadedRate limiting and lockout on repeated failed authentication attempts
WPS Hide LoginRelocates the login URL, removing the default endpoint from automated scanning and credential-stuffing traffic

Each operates at a different point in the request path — the firewall inspects traffic, the rate limiter governs authentication behaviour, and the login relocation reduces the volume of automated traffic that reaches either. Removing any one of them does not have its function absorbed by the others.

We acknowledge that Wordfence includes its own brute-force lockout capability, which is the overlap the audit identified. We are happy to document the current configuration of both so that enforcement ownership is explicit, rather than deactivating a control on the assumption that another covers it.

Temporary Login Without Password is a separate matter. The audit's concern about standing privilege-escalation surface is reasonable, and we agree it should be removed if it is not in active use.

5.3 Google Site Kit connection status

Both audits note that Site Kit is present but unauthenticated, and treat the disconnected state as a defect to be remediated or the plugin removed. The plugin is installed; it has not been connected or configured, and this is intentional.

The ecommerce portion of the website has not gone live. Our standard process is to install and configure Site Kit as part of the marketing setup phase, alongside Google Analytics and conversion tracking and Google Merchant Center, once the ecommerce portion is ready for launch. Merchant Center in particular requires active products and SKUs to be mapped to the feed.

Configuring analytics before then would mean tracking against a checkout and purchasing flow that is still changing. Connecting Site Kit at launch instead ensures that conversion tracking, ecommerce events and merchant data are all configured against the final live flow, rather than being set up twice.

Site Kit is not required for WooCommerce to function, so its unconnected state has no effect on the current development of the online store. We would recommend leaving it in place: it is inert while unauthenticated, and removing it now would only mean reinstalling it when the launch and marketing phase begins.

6. WP_DEBUG status

Both audits correctly report that WP_DEBUG is enabled in production, and we acknowledge the finding.

For context: following the 27 August work, debug logging was re-enabled deliberately while we investigated the performance issues that led to the OPcache and PHP changes described above. It is a diagnostic measure rather than an oversight, and display output remains off, so errors are written to log rather than rendered to visitors.

With the OPcache work now settled and the runtime on a supported version, the main reason for keeping it on has largely passed. We will disable WP_DEBUG once we have confirmed stable origin behaviour over a monitoring window, and will confirm the date when we do.

Two related points we would rather state than have asked.

First, on the log itself. WP_DEBUG_LOG is configured to write to /home/ccpatpvlive/logs/, which sits above the web root and has no URL that maps to it. We have also checked the default WordPress location: a request for the wp-content debug log path returns HTTP 403 rather than serving a file. We are completing that check at the filesystem level before treating it as closed, since a 403 confirms the path is refused but not that no file exists there. We raise it because a reachable debug log is a real information-disclosure route, and a site that has had debug logging on for a period is exactly where one would look.

6.1 Change communication

The changes described in this document — the debug toggle, the OPcache override, the PHP 8.3 upgrade, the PHP 8.4 attempt and rollback, and the Redis object cache install — were not communicated to CC Patio as they were made. This document is the first notification of them. That is a gap in our process rather than in the work itself, and we would rather name it here than have it surface as a question later.

Going forward, we propose that production changes affecting runtime, caching, or configuration are notified at the time they are made, with a short written record of what changed and why, and that anything carrying rollback risk is scheduled rather than applied ad hoc. We are happy to agree a format for that with CC Patio and the reviewing team.

7. Broken Link Checker scheduling

The client report characterises Broken Link Checker as continuously crawling and writing to the database, and rates immediate deactivation as CRITICAL.

The plugin is configured to run on a three-day interval, not continuously. It supports the digital marketing team's link integrity checks, with particular value across weekends when no one is actively monitoring the site. Crawl scheduling is a plugin setting and is not reported in a Site Health dump, which we suspect is why the assessment assumed a continuous crawl.

We would also note the read-only audit's link findings, which bear on how much load this plugin is actually generating. Its raw scan produced 140 candidate references across 57 unique targets, but public HTTPS validation of every one of those targets reduced this to two genuinely broken paths across four references. The remaining targets resolve directly or through working redirects. A catalog of this size with two broken internal links does not suggest a plugin under heavy load.

That said, we are open to moving the crawl to an off-peak window, or to running it via WP-CLI on a schedule rather than through the plugin's own cron, if that would satisfy the concern. We would want to retain the capability itself, as the marketing team relies on it.

Summary

Of the issues raised, the PHP end-of-life finding, the OPcache saturation finding and the missing persistent object cache were all actioned on the day the audit was received, and the OPcache occupancy figures in §3 close the item neither audit could verify. Six further findings reflect configuration, component relationships or project sequencing that the available evidence did not show: cache ownership, the theme-and-builder distinction, the security stack's layered roles, Site Kit's connection status, Broken Link Checker scheduling, and the reason WP_DEBUG is currently enabled.

We have also raised three items against ourselves that the audit did not identify: the PHP 8.4 attempt was made on production rather than the development site, the debug log location is being confirmed at filesystem level, and production changes have not been communicated to CC Patio as they were made. The remaining items in the table above are accepted and tracked. We are happy to prioritise them against whatever sequence CC Patio and the reviewing team consider most useful, and to provide host-level evidence for any item where a snapshot alone would leave ambiguity.
