Subject: CC Patio — Required infrastructure clarifications before OPcache / cache remediation Hello — Our stability audit of www.ccpatio.com was based on the WordPress Site Health diagnostic dump only. That gives us strong visibility into the application layer, but we lack authoritative detail on edge routing, LiteSpeed/server config, NitroPack SaaS behavior, and deployment/change pipelines. Before any OPcache resizing or caching-stack changes proceed, please answer the questions below so we share a single, complete architecture map. Please respond with concrete values (screenshots or exported rules accepted) rather than generalities. Thank you, Robert J Gutierrez
Why this is blocking. Site Health confirmed OPcache FULL, NitroPack + advanced-cache.php, and Cloudflare in front of LiteSpeed — but not how those layers are configured to interact. Remediating OPcache while the wrong cache owner still purges/loopbacks will not clear 522s.

A. Ownership & access

  1. Who is the authoritative owner of the Cloudflare zone for ccpatio.com / www.ccpatio.com (PrimeView, host, or client), and who can export DNS, Page Rules, Cache Rules, WAF, and Analytics? Blind spot: we cannot validate edge behavior without zone ownership clarity.
  2. Who controls the LiteSpeed / hosting panel for ccpatpvlive (cPanel, CyberPanel, DirectAdmin, managed LiteSpeed), and can you provide read-only access or exported PHP / OPcache / LSAPI settings? Blind spot: Site Health shows PHP limits, not worker pools or OPcache ini.
  3. Who owns the NitroPack account bound to this site, and can you export (or screenshot) Optimization, Cache, and CDN settings as of today? Blind spot: SaaS-side config is invisible from Site Health.

B. Cloudflare edge & origin path

  1. Is the orange-cloud (proxied) status enabled for www and apex? List any DNS records that bypass Cloudflare (grey-cloud, direct A/AAAA to origin). Blind spot: partial proxying explains inconsistent 522 patterns.
  2. What is the exact origin hostname/IP Cloudflare connects to, and is origin pull over HTTPS with Full (strict), Full, or Flexible SSL? Blind spot: SSL mode and origin identity affect handshake failures misread as 522s.
  3. Provide the current Cloudflare Cache Rules / Page Rules / Configuration Rules that affect HTML, /wp-admin, /wp-json, WooCommerce cart/checkout, and static assets (Cache Everything, Bypass, Edge TTL, Browser TTL). Blind spot: competing HTML cache at edge vs NitroPack is a primary 522 amplifier.
  4. Is Cloudflare APO for WordPress, Argo, or any Polish/Mirage/Auto Minify feature enabled? If APO is on, is the WordPress plugin installed or was it removed? Blind spot: APO + NitroPack is a known double-optimization conflict.
  5. What are the Cloudflare origin connection timeout / proxy read timeout settings (default vs Enterprise custom), and how many 522 / 524 events occurred in the last 14 and 30 days (path + country breakdown if available)? Blind spot: we inferred 522s from ops reports; need edge telemetry.
  6. Are there Cloudflare Workers, Transform Rules, or Load Balancers in the request path for www.ccpatio.com? Blind spot: Workers can add latency or origin fan-out invisible to WordPress.
  7. Confirm canonical host policy: apex ccpatio.com vs www.ccpatio.com — which redirects where (Cloudflare rule vs WordPress vs .htaccess), and is Search Console verified on the same host Rank Math / Site Kit use? Blind spot: Site Kit showed www reference URL vs apex SC property.

C. LiteSpeed / PHP / OPcache (server plane)

  1. Export current PHP / OPcache settings: opcache.memory_consumption, opcache.interned_strings_buffer, opcache.max_accelerated_files, opcache.revalidate_freq, opcache.validate_timestamps, JIT status (on/off), and whether OPcache is per-vhost or global. Blind spot: Site Health only showed FULL + 56.6% hit rate — not tunables.
  2. What are LiteSpeed PHP LSAPI / external app limits for this vhost: max connections, max idle time, process soft/hard limits, and current peak concurrency during business hours? Blind spot: 522s often mean exhausted workers, not “slow PHP” alone.
  3. Is LiteSpeed Cache (LSCWP) installed or was it previously used? Is there any server-level cache (LSCache, Redis object cache, Memcached) in front of or beside NitroPack? Blind spot: third cache tier may exist outside the plugin list.
  4. What is the hosting plan resource envelope (vCPU, RAM, IOPS, inode limits), and have you observed CPU steal, disk wait, or inode pressure coinciding with 522 windows? Blind spot: application dump cannot show noisy-neighbor / I/O saturation.
  5. Confirm MariaDB location (same host vs remote), whether query cache / slow-query log is enabled, and current max_connections utilization at peak. Blind spot: 518 MB DB size ≠ connection or lock contention profile.

D. NitroPack SaaS ↔ origin interaction

  1. Is NitroPack configured for HTML caching, image optimization, font optimization, and/or remote “optimizer” fetches that cause the origin to request itself (loopback)? Provide the setting names as shown in the NitroPack dashboard. Blind spot: loopbacks under full OPcache are a classic 522 generator.
  2. What is NitroPack’s purge policy on WooCommerce product/stock updates, Elementor saves, and Rank Math changes — instantaneous full-site purge, targeted URL purge, or queued? Blind spot: purge storms explain intermittent cold-start clusters.
  3. Does NitroPack’s CDN serve HTML and assets from NitroPack’s network, Cloudflare, or both? Clarify the TLS certificate and cache key strategy for personalized / cart cookies. Blind spot: dual CDN ownership breaks cookie/cache correctness and debugging.
  4. Are there NitroPack exclusions for cart, checkout, my-account, wp-admin, REST API, and Gravity Forms confirmation pages? Paste the exclusion list. Blind spot: missing exclusions cause cache poisoning or forced origin hits.

E. Deployment, cron, and change pipeline

  1. How are production code and plugin/theme updates deployed (SFTP, Git pull, CI/CD, host panel)? Is there a staging hostname with the same LiteSpeed/PHP/OPcache/Cloudflare topology? Blind spot: “fragile staging” may not mirror production edge/server config.
  2. Is system cron or WP-Cron used? List high-frequency Action Scheduler / cron jobs (Broken Link Checker, NitroPack, WebToffee feeds, Rank Math, Wordfence scans) and their schedules. Blind spot: background load can starve LSAPI during catalog hours.
  3. What is the change-control process for enabling/disabling caching plugins, and has NitroPack or Cloudflare Cache Everything been toggled during the period of intermittent 522s? Blind spot: recent config churn may be the proximate cause.
  4. Confirm whether object caching (Redis/Memcached via Drop-In) is planned or already present outside WordPress’s reported drop-ins (we only see advanced-cache.php). Blind spot: missing object-cache.php in Site Health may still mean server Redis unused by WP.

F. Security / WAF / access path (affects origin load)

  1. Are Cloudflare WAF managed rules, Bot Fight Mode, or rate limits active on wp-login / xmlrpc / checkout? Do they challenge legitimate optimization or monitoring user-agents (NitroPack bots, uptime checks)? Blind spot: challenged optimizer bots retry and amplify origin load.
  2. What is the real wp-login URL under WPS Hide Login, and are uptime monitors hitting a 404/redirect loop that still burns PHP workers? Blind spot: health checks against a hidden login can look like origin failure.

Requested deliverables (please attach)

  1. Cloudflare: DNS export + Cache/Page/Config rules export (or screenshots) + 14-day 5xx analytics.
  2. Server: PHP info / OPcache ini + LiteSpeed external app limits for this vhost.
  3. NitroPack: dashboard settings export/screenshots + exclusion list + purge policy.
  4. One diagram or bullet path: Client → Cloudflare → (optional NitroPack CDN) → LiteSpeed → PHP LSAPI → MariaDB with “cache yes/no” at each hop.
  5. Written confirmation of the single intended HTML cache owner going forward: Cloudflare XOR NitroPack (not both).
Remediation sequencing. Please do not begin OPcache resizing or cache-plugin cutovers until items A–D are answered and we jointly sign off on the single cache owner. OPcache work without edge clarity risks masking 522s rather than eliminating them.
