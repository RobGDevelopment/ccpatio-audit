2. Purpose and posture

This document is the formal CC Patio response to PrimeView’s Remediation Record and Audit Response dated 18 September 2026 and to the accompanying support note from John P. It is issued in the same series as the WordPress Architectural & System Stability Audit and the External Origin Stability & Caching Telemetry Report. It is a record for PrimeView engineering, CC Patio executives, and the reviewing team. It is not a support email.

Where PrimeView’s live evidence corrects a Site Health limitation, that correction is accepted and cited. Where PrimeView restates a finding as closed without the acceptance criteria published on 18 September, the finding remains open. Where PrimeView admits a process failure, that admission is taken as the basis for the protocol below.

Two secondary Cloudflare statements remain imprecise and should be corrected in PrimeView’s next written update, without reopening ownership:

  • John P. wrote that Cloudflare is “not currently being used as a caching or performance layer,” and that Edge Analytics, WAF, and Cache Rules are “not being used to speed up the site.” Remediation record §4 states that Cloudflare “sits in front as a reverse proxy and WAF” and that “Cloudflare caches static assets (CSS, JS, images, fonts) by default on any proxied zone.” Default static-asset caching is a caching layer. PrimeView states that nothing was damaged and that no data was affected. That is an assertion. The logs required in §8 will decide. Emergency 512 MB OPcache override Admitted

Redis object cache enabled on live Admitted
Installed and enabled on production the same day. No staging soak. PrimeView will “monitor hit ratio and watch for serialization errors.” Serialization, stale-object, and session impact on a Woo + Elementor catalog remain unverified.

7. SRE assessment — the 20.5-second origin stall

The external endurance run is the measurement PrimeView’s closure sentence has to survive. It has not been repeated since the unannounced changes.

A 200 after 20.5 seconds is a near-miss 522, not a healthy origin. Cloudflare did not fail. The origin stalled on a single sequential cache-busted request. The edge waited; this time it did not give up. Catalog mode was still on. Transactional WooCommerce traffic has not been enabled. The stall occurred before checkout load.

What each change can explain

  • 512 MB OPcache is the only change that addresses the evidenced compile-thrash mechanism. Occupancy ~225/512 MB is necessary and not sufficient. Hit rate remains unpublished. Acceptance is still ≥90% and opcode_cache_full=false.
  • PHP 8.3.33 closes the EOL security finding. It is not a twenty-second cliff fix.
  • Redis should reduce repeated options / transient / taxonomy queries on the 685–932 ms median MISS band. It does not, by itself, prevent a lockup-class stall, and it adds serialization risk on an unstaged catalog.
  • PHP 8.4 on live is the opposite of remediation. Broken templates mean workers served fatals or incomplete renders. Every PHP version switch wipes OPcache.

Why §2’s closure sentence is rejected

  • The published model was OPcache saturation as the primary runtime defect, plugin boot and ~3.3 MB Elementor HTML as amplifiers, and Cloudflare as the timeout observer. PHP EOL was a separate critical security finding — not half of a two-factor exclusive model.
  • The path 8.2 → 8.3 → 8.4 → 8.3 is three cold-cache events on production in one day. A 20.5 s first-byte delay is the signature of a cold, heavy PDP filling a new opcode slab under 38 plugins.
  • If the 20:02Z window overlapped that work, attempt 3 may be a live observation of the change window. Exact UTC timestamps were not published.
  • No Repeat-MISS re-run. No 72-hour Cloudflare 5xx from the CC Patio zone. Redis, two PHP upgrades, and an emergency ini are one confounded change set.

8. Protocol now in force

CC Patio formally accepts the process PrimeView proposed in its §6.1 and the open-item handling in its §8, and elevates both to the following operating protocol for ccpatpvlive. This protocol is effective on the date of this document.

8.1 Feature freeze In force
No net-new storefront, builder, catalog-import, feed-regeneration, or configurator work on production until the 18 September stability gate is evidenced: OPcache not full and hit rate ≥90%; single HTML cache owner documented from the CC Patio zone; Broken Link Checker off business-hours crawl; WP_DEBUG false; seventy-two hours with zero unexplained Cloudflare 522s; Repeat-MISS endurance on Brooklyn Corner Sofa with no multi-second TTFB cliffs.
8.2 Prior written notification In force
No further production changes to PHP, OPcache, object cache, LiteSpeed, wp-config.php, caching plugins, or security plugins without prior written notification to CC Patio and the reviewing team. Contemporaneous notice after the fact, as described in PrimeView §6.1, is not compliance.
8.3 Staging first for rollback-risk work In force
Anything with rollback risk — including the PHP 8.4 retry already described in PrimeView §2, WooCommerce 11.1.1, revision cleanup, temporary-table removal, DISALLOW_FILE_EDIT, and WP_DEBUG disable — is executed on the development / staging site first, with a written rollback path, and is not applied to ccpatpvlive ad hoc. This is the method PrimeView has already written for the 8.4 retry. It now applies to the full change set.
8.4 Log preservation In force
Yardi cPanel access is welcomed. Until the reviewing team has copied them off the host, the following must be preserved without truncation, rotation, or wipe: /home/ccpatpvlive/logs/ in full (including ccp-wp-errors.log); LiteSpeed / web-server error and access logs for ccpatpvlive; PHP / LSAPI logs for the 18 September window (8.2 → 8.3, the 8.4 attempt and revert, the 99-opcache-custom.ini deploy, and Redis enablement); and any host or panel logs that timestamp those changes. PrimeView §6 notes the configured debug path sits above the web root; that tree is the contemporaneous record of the unannounced change window.
