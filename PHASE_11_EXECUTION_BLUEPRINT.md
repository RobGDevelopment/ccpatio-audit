## 0. WHAT THE OWNER DIRECTIVE REQUIRES
Four binding mandates (the Owner's wording is the authority, this section only restates them as testable requirements):
M1. PRE-KATANA PAUSE (zero ghost demand). NO Katana interaction of ANY kind happens until a deposit clears or management overrides. "Any kind" includes the Sales Order, the Manufacturing Orders, AND the catalog writes that exist only to support them (variant creation, recipe/BOM publish). Consequently NO Katana delete or compensation executor exists in this phase. Unpaid orders never exist in Katana, so there is nothing to undo.
M2. STATELESS RESUME. No `waitForEvent`, `sleep` or `sleepUntil` holds a deal open while it waits for money. Function 1 (CAD Handoff) ends and uses zero compute. Function 2 (Katana Release) is a separate Inngest function triggered by `path-a/release-to-production`, fired by either the Next.js UI (Management Override) or the future QBO ledger leg (Customer Deposit). A deal may wait 60, 120 or 365 days with no timer, no timeout and no silent drop.
M3. MULTI-SKU OPPORTUNITIES. One GHL Opportunity is one backyard deal and maps to many custom SKUs. All SKUs aggregate under one `ghl_opportunity_id`. Function 2 pushes ONE Katana Sales Order with one line per SKU and one MO per line. The finalized BOM and SKU list are written back to the GHL Opportunity so showroom staff never leave GHL.
M4. ROLE-BASED AUTH STUB. No `.env` allowlist and no hardcoded email decides override authority. The Server Action `canOverrideDesign` reads a generic `session.ghl_role` and fails closed when it is missing or insufficient. GHL SSO will populate it later.

### 0.1 ARCHITECT FINDINGS (each verified against the repo on 2026-10-13; they shape the design)
F1. THE SCHEMA ALREADY FORBIDS "MANY JOBS PER OPPORTUNITY". `custom_build_jobs.ghl_opportunity_id` is `UNIQUE` (migration 0052, `schema.ts` `custom_build_jobs`), and `mintCustomJob` deliberately reuses one header per opportunity. The header is therefore already the opportunity-level aggregate, and each custom SKU hangs off it only through the JSON attribute `sku_mappings.attributes.job_id`. That linkage is not relational, not queryable per SKU, and has no per-SKU design state. Dropping the unique constraint would break "additive schema only" and every reader that assumes 1:1. See D1.
F2. THE SESSION HAS NO ROLE. `PimSession` is `{ email: string; name: string }` (`src/lib/pim-audit.ts`). `getPimSession()` resolves an e2e cookie, a Supabase user, or the synthetic embed principal `ghl-embed@ccpatio.com`, and none of them carries a role. A separate `user_roles` table (SuperAdmin / IT_Admin) exists for Mission Control only. The directive says to read `session.ghl_role`, so the stub is a typed, optional, additive extension of `PimSession`. Nothing populates it yet, which means EVERY override is denied in production until GHL SSO lands (operational consequence in section 9).
F3. TODAY'S "RELEASE TO KATANA" BUTTON IS THE GHOST-DEMAND PATH. `Step4Release.tsx` calls `publishApprovedRecipeToKatana(rootSku)` and then, for `JOB-` SKUs, `releaseCustomJobAction`, which emits `factory.custom_job.released`. `releaseCustomJob` runs `executeReleaseCustomBuild`, which POSTs (or PATCHes) a Katana Manufacturing Order with NO sales order and NO payment check when `GHL_FACTORY_ORDERS=live`. It also stamps a cut-card URL on the MO. Both writers must be neutralized for custom SKUs, and the cut-card stamp must move into Function 2.
F4. THE RECIPE PUBLISH MIXES HUB WORK WITH KATANA WORK. `publishApprovedRecipeToKatana` (`src/app/admin/factory-bom/actions.ts`, from about L1132) does hub-side finalization first (airlock evaluation, shop-drawing PDF and `product_assets` rows, dossier hash, `approveDraftRecipe`, release-gate hash) and only then writes Katana (`syncBOMToKatana`, which may call `ensureKatanaVariantForSku`). It also calls `requireSession()` and lives in a `"use server"` file. Inngest cannot call it as it stands. The split into a hub-only half (before the pause) and a Katana-only half (Function 2) is mandatory.
F5. `saga_status` HAS SIX VALUES and no pause state (`PENDING`, `IN_PROGRESS`, `COMPLETED`, `COMPENSATING`, `COMPENSATED`, `SAGA_FAILED_REQUIRES_MANUAL_INTERVENTION`; migration 0054). `saga_runs` has no release or deposit columns. The journal has 56 entries and the last tag is `0054_sre_dlq_saga_buckets`, so the next migration is `0055`.
F6. THE CONVERTER IS SYNCHRONOUS AND `.blend`-ONLY. `services/cad-convert/app.py` exposes only `POST /convert`, answers `415 SKP_CONVERT_UNAVAILABLE` for `.skp`, and `process-job.ts` calls `convertBlendToGlb` (a 120 s `fetch`) inside the `process-cad-bytes` step. No callback route exists (`src/app/api/webhooks/` holds clover, ghl, katana, sketchup, woocommerce). `/api/inngest` exports no `maxDuration`. The roadmap's ".skp parsing" does not exist and is not invented here.
F7. THE `order.approved` LANE ALREADY OWNS `GHL-<oppId>` AND `order_intake.katana_*`. `runApprovedFactoryOrder` creates Sales Order `GHL-<oppId>` for catalog `FIN-` lines and writes `order_intake.katana_sales_order_id / katana_order_no / katana_mo_ids`. Path A must use a different order number and must not write those columns, or the two lanes will adopt or overwrite each other's orders.
F8. GHL WRITE SURFACE. `src/server/ghl/private-api.ts` has `ghlGet / ghlPost / ghlPut / ghlDelete` and `updateOpportunityValue`. The only existing write-back is a contact note or task (`hold-warning.ts`). No opportunity custom-field writer and no custom-field id configuration exist. GHL endpoint shapes are NOT verified here: the Builder verifies them against GHL's current API documentation and records the source in the handback (no live GHL call is allowed to "check").
F9. INNGEST RUN-LENGTH CAP IS MOOT BY DESIGN. Inngest caps total run length including waits (30 days Free, longer on paid plans) and silently cancels an over-limit run. The stateless design removes the failure mode entirely: no run is ever open while a deal waits.
F10. LIVE-DB STATE. The Owner states the live DB is fully synchronized with the codebase through 0054. The Phase 10 handback (section 2) said migrations 0046 to 0054 were not applied live at that time. The Builder re-verifies read-only (Task 0). Migration 0055 is applied to the live DB by the OWNER only, never by the Builder.
F11. LEGACY TESTS ENCODE THE OLD ASSUMPTION. `tests/custom-build-job.test.ts` (DB-excluded), `tests/publish-idempotency.test.ts`, `tests/woo-static-guards.test.ts` and `tests/sre-katana-throttle.test.ts` reference `executeReleaseCustomBuild`, `releaseCustomJob`, `publishApprovedRecipeToKatana` or `custom_build_jobs`. Before touching any of them read them, list in the handback every assertion that changes (before and after) and why. Never weaken a test to force a pass (.cursorrules). A test that asserts the old "release writes a Katana MO before payment" behavior for a custom SKU is an assertion the Owner has overruled; changing it needs QC sign-off.

### 0.2 DECISIONS AND DEPARTURES FROM THE LITERAL BRIEF (recommended defaults are binding unless QC or the Owner overrules BEFORE the build starts)
D1. MULTI-SKU MODEL: `custom_build_jobs` STAYS the 1:1 opportunity header (its UNIQUE constraint is kept). A NEW additive child table `custom_build_job_items` (one row per custom SKU, FK to the header) carries the per-SKU design state. "Multiple custom_build_jobs under one opportunity" is therefore delivered as "multiple SKUs under the one job header for that opportunity". Rejected: dropping the UNIQUE constraint (violates additive-only; breaks `mintCustomJob`, which reuses the header by design).
D2. WHERE `AWAITING_DEPOSIT` IS SET: a CAD callback alone never yields a releasable BOM, because the human airlock (cut-list, operations and identity checklist) sits between the converter's drafts and a finalized BOM. Pushing an unreviewed BOM to Katana the moment a deposit clears would be worse than the problem being solved. So: Function 1 ends with the item at `needs_review`; the human "Finalize design" action (hub-side only, no Katana) is what moves the item to `finalized` and the saga to `AWAITING_DEPOSIT`. Function 1 still "receives the callback and cleanly terminates"; the saga status flip happens one human click later. QC may overrule, but then Function 2 would release unreviewed BOMs.
D3. THE ONLY `waitForEvent` IN PATH A is the converter callback wait inside Function 1: bounded, default 30 minutes, clamp 1 to 120. Roadmap §2 requires it and a lost callback must fail loudly (DLQ alert), not strand an upload. It is a minutes-scale wait on infrastructure, not a deal wait. Static guards (Task 10) enforce that no `waitForEvent`, `sleep` or `sleepUntil` exists anywhere after the item reaches `needs_review`, in Function 2, or in the GHL sync function. Fully stateless alternative if QC prefers zero waits everywhere: split Function 1 into dispatch plus a callback-triggered completion function and show a "converting for N minutes" badge instead of a timeout. State the choice in the handback.
D4. THE PAUSE COVERS CATALOG WRITES TOO (M1, "any Katana interaction"). Variant creation and recipe publish for a custom SKU move behind the release gate into Function 2. Raw-material variants already exist in Katana and are only read from the hub DB.
D5. KATANA WRITE FENCE, FAIL CLOSED. Every `custom_build` SKU (`sku_mappings.attributes.custom_build === true`) is fenced from Katana writes until its opportunity's saga has a recorded release and has been claimed by Function 2 (Task 3). A custom SKU whose job has NO `ghl_opportunity_id` has no deposit to gate on, so it is blocked from Katana entirely in this phase with a clear error ("attach a GHL opportunity"). Alternative (leave opportunity-less custom jobs on the legacy writer) leaves a ghost-demand hole and is rejected. A missing 0055 schema also blocks (fail closed), the opposite of "dormant".
D6. NO EXPIRY, NO TIMEOUT, NO COMPENSATION. A deal in `AWAITING_DEPOSIT` has no deadline and nothing consumes it. The UI shows its age. "Deal lost / cancel package" handling is out of scope (it is DB-only and trivial, but not requested). Failures after the release claim are retried and, when terminal, go to `SAGA_FAILED_REQUIRES_MANUAL_INTERVENTION` with the partial Katana state left in place and idempotently resumable. Nothing is ever deleted.
D7. DB FIRST, EVENT SECOND. The authorization to release is a DB row (`saga_runs.release_requested_*`, first writer wins). The Inngest event only wakes Function 2, which trusts the row and never the payload. A forged `path-a/release-to-production` event with no recorded request does nothing.
D8. EARLY DEPOSITS ARE REAL (§2.5: Clover collects the deposit first). A deposit that arrives while the design is not finalized is recorded as a durable release request and replayed by the Finalize action when the saga reaches `AWAITING_DEPOSIT`. It is never dropped and never parked in a timer.
D9. `log` MODE PAUSES TOO. With `GHL_FACTORY_ORDERS=log` the whole loop (CAD, finalize, pause, override, release request) runs and the UI works, Function 2 makes ZERO Katana calls and the saga stays `AWAITING_DEPOSIT` (never `COMPLETED`), so it can be re-fired after the live flip (replay tooling is step 9).
D10. Sales Order price stays `0` (the quote and ledger live in QBO per §2.4/§2.5, same as the existing GHL factory lane). Phase 11 requires integer-cent `deposit_cents > 0` on a deposit and does no arithmetic on it. No minimum-deposit policy here (step 8).
D11. `.skp` stays fail-closed (`SKP_CONVERT_UNAVAILABLE`). Only `.blend` goes async, in BOTH CAD lanes (catalog and Path A), because the 120 s synchronous fetch inside a step is the Vercel hazard in either.

## 3. STATE MACHINE DEFINITION (single source of truth for Tasks 1 to 10)
Saga type `path_a_cad`. `correlation_key` = the GHL opportunity id (string). It is the only identifier shared by CAD, Finalize, deposit, override and release.

### 3.1 The three zones
| Zone | Saga status | Katana objects exist? | Compute held? | What can happen |
|---|---|---|---|---|
| A. Design | `PENDING` (`designing`, `cad_dispatched`, `awaiting_design_review`, `design_changed`, `cad_failed:<code>`, `deposit_received_early`) | NO | Function 1 only while the converter runs (minutes) | Upload, convert, review, finalize, re-upload |
| B. Pause | `AWAITING_DEPOSIT` (`awaiting_deposit_or_override`, `release_dry_run:<source>`) | NO | NONE. No run, no timer, no timeout | Waits any length of time. Only a DB row change plus an event ends it |
| C. Release | `IN_PROGRESS` (`releasing`) then `COMPLETED` (`released_to_production`) or `SAGA_FAILED_REQUIRES_MANUAL_INTERVENTION` (`release_failed:<leg>`) | YES, only from here | Function 2, seconds to minutes | Recipe publish, one SO, N MOs, cut-card stamps. Retry, never delete |

### 3.2 Saga transitions (`saga_runs.status`)
| From | To | `current_step` | Set by | Guard |
|---|---|---|---|---|
| (no row) | `PENDING` | `designing` | Function 1 `ensure-item`, or the early-deposit seam (`deposit_received_early`) | `insertOnce` on (`path_a_cad`, oppId) |
| `PENDING` | `AWAITING_DEPOSIT` | `awaiting_deposit_or_override` | Finalize action (`advanceSaga`) | item count >= 1 AND every item `finalized` AND no item in `awaiting_cad` / `needs_review` / `cad_failed` |
| `AWAITING_DEPOSIT` | `PENDING` | `design_changed` | re-upload or design invalidation | status is exactly `AWAITING_DEPOSIT` (never once `IN_PROGRESS` or later) |
| `AWAITING_DEPOSIT` | `AWAITING_DEPOSIT` | `release_dry_run:<source>` | Function 2 in `log` mode | no Katana call, status unchanged |
| `AWAITING_DEPOSIT` | `IN_PROGRESS` | `releasing` | Function 2 `claim-release` | `release_requested_at IS NOT NULL` AND live mode |
| `IN_PROGRESS` | `COMPLETED` | `released_to_production` | Function 2 `finalize-saga` | every item `released` |
| `IN_PROGRESS` | `SAGA_FAILED_REQUIRES_MANUAL_INTERVENTION` | `release_failed:<leg>` | Function 2 failure handler, paired with a thrown `NonRetriableError` | scrubbed `last_error`; partial Katana state is left in place |
| `SAGA_FAILED_...` | `IN_PROGRESS` | `releasing` | Function 2 resume | `release_requested_at IS NOT NULL` (the authorization already exists). All steps are idempotent |
`COMPENSATING` and `COMPENSATED` are NEVER used by `path_a_cad`.

### 3.3 Item transitions (`custom_build_job_items.design_status`)
`awaiting_cad` -> `needs_review` (Function 1 success) | `cad_failed` (Function 1 data failure or callback timeout). `needs_review` -> `finalized` (Finalize action). `finalized` -> `needs_review` (design invalidated, see Task 5) or `awaiting_cad` (re-upload). `finalized` -> `released` (Function 2, per item, after its MO exists). `released` is terminal. A re-upload is REJECTED (clear error, no mutation) once the saga is `IN_PROGRESS`, `COMPLETED` or manual-after-claim: post-release changes are a change order and out of scope.

### 3.4 Events (only event ids built through `inngestEventId`; payloads carry ids, never secrets)
| Event | Emitted by | Consumed by | Event id |
|---|---|---|---|
| `cad/model.uploaded` (existing) | upload confirm | Function 1 | existing |
| `cad/convert.completed` | signed callback route | Function 1 (bounded wait) | `cad:convert:<uploadId>:<status>` |
| `path-a/design.finalized` | Finalize action | GHL sync | `path-a:finalized:<sku>:<dossierHash>` |
| `path-a/release-to-production` | Override action, deposit seam, Finalize replay, Retry release | Function 2 | `path-a:release:<oppId>:override` / `...:deposit:<ref>` / `...:replay:<n>` / `...:retry:<n>` |
| `path-a/release.completed` | Function 2 final step (`step.sendEvent`) | GHL sync | `path-a:completed:<oppId>` |
| `path-a/ghl.sync.requested` | UI "Re-sync GHL" | GHL sync | `path-a:ghl-sync:<oppId>:<n>` |
Retry and replay discriminators come from the recorded `release_attempts` counter so a deliberate re-send is never swallowed by Inngest's event-id dedupe.

### 3.5 The three Inngest functions (the whole runtime surface)
1. FUNCTION 1 — CAD HANDOFF = the existing `process-cad-upload` (`cad/model.uploaded`), extended. Dispatches the async converter (fire-and-forget HTTP 202), receives the signed callback via the single bounded wait, runs the existing draft/BOM extraction, sets the item `needs_review` and the saga row `PENDING / awaiting_design_review`, and TERMINATES. Holds nothing afterward.
2. FUNCTION 2 — KATANA RELEASE = NEW `path-a-release-to-production` (trigger `path-a/release-to-production`). Fully independent of Function 1. Reads state from the DB, authorizes from the recorded request, writes Katana, marks the saga `COMPLETED`. No waits.
3. GHL SYNC (lightweight sibling) = NEW `path-a-ghl-sync` (triggers `path-a/design.finalized`, `path-a/release.completed`, `path-a/ghl.sync.requested`). Recomputes the payload from the DB on every run. Failure never blocks the saga or Katana.
Finalize, Override and the deposit seam are DB-first server code (not Inngest functions): they write the row, then send the event.

### 3.6 Authority fences (what proves "zero ghost demand")
1. The Task 3 fence blocks every Katana write path for a custom SKU until the saga is `IN_PROGRESS` or `COMPLETED` with a recorded request.
2. Function 2 refuses to act without `release_requested_at` (forged events are inert).
3. Function 2 refuses to act unless every item is `finalized` and each item's `finalized_dossier_hash` equals the current `factory_release_gate.dossier_hash` (a design edited after finalize is a manual state, caught before any Katana call).
4. Static guards forbid any Katana DELETE, any wait primitive, and any Katana import from the pre-release modules (Task 10).
